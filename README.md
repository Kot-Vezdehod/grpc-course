# grpc-course

Учебный проект на Go: система товаров, заказов и платежей с HTTP API и
взаимодействием сервисов по gRPC. Проект демонстрирует разделение domain,
application и adapters, работу с PostgreSQL, резервирование остатков и mTLS.
Payment сохраняет записи о платежах; интеграции с платёжным провайдером нет.

## Архитектура

| Компонент | Ответственность | Локальный адрес |
| --- | --- | --- |
| API Gateway | REST/JSON API, преобразование запросов и ошибок gRPC | HTTP `:8080` |
| Order | Резервирование товара, сохранение заказа, создание платежа | gRPC `localhost:50051` |
| Inventory | Создание и получение товаров, учёт остатков и резервов | gRPC `localhost:50053` |
| Payment | Хранение платежей с уникальным `order_id` | gRPC с mTLS `localhost:50052` |

У каждого сервиса собственная PostgreSQL-база. Создание заказа выполняется
последовательно: резерв Inventory → сохранение Order → вызов Payment.
mTLS используется между Order и Payment; остальные gRPC-соединения — без TLS.
[Описание архитектуры](docs/architecture.md) содержит диаграммы компонентов
и последовательности операций.

## Технологии и возможности

- Go 1.27, gRPC, Protocol Buffers, HTTP и JSON.
- PostgreSQL, pgx через `database/sql`, Squirrel, миграции Goose.
- Создание и чтение товаров, атомарное резервирование остатка в PostgreSQL.
- Заказы с одной позицией, проверка входных данных и преобразование ошибок в HTTP.
- Идемпотентный эффект повторного резервирования и платежи с уникальным `order_id`.
- mTLS, ограниченные повторы вызовов Payment и circuit breaker.
- Структурированные логи slog, метрики Prometheus.
- Unit-тесты, интеграционные тесты с Testcontainers и отдельный E2E-сценарий.

## Локальный запуск

Требуются Go 1.27.1 или новее в ветке Go 1.27, PostgreSQL 18, Goose CLI,
OpenSSL и Bash. Docker необходим для Testcontainers. Сгенерированные protobuf
Go-файлы включены в репозиторий; обычная сборка не требует protoc.

```bash
go mod download
go build ./...
```

Каждое приложение использует обязательную переменную подключения к своей базе:

| Приложение | Переменная |
| --- | --- |
| Order | `ORDER_DATABASE_URL` |
| Inventory | `INVENTORY_DATABASE_URL` |
| Payment | `PAYMENT_DATABASE_URL` |

Fallback DSN отсутствуют; пустая конфигурация приводит к ошибке при запуске.
Файлы `.env` автоматически не загружаются. Перед запуском необходимы миграции
и локальные сертификаты для Order и Payment.

Пошаговое руководство: [PostgreSQL, DSN, миграции и запуск четырёх приложений](docs/local-development.md).
Настройка сертификатов: [локальный mTLS](docs/mtls.md).

## HTTP API

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/health` | Проверка ответа Gateway |
| POST | `/api/v1/inventory` | Создание товара |
| GET | `/api/v1/inventory/{id}` | Получение товара и остатка |
| POST | `/api/v1/orders` | Создание заказа |

```bash
curl http://localhost:8080/health
```

Ожидаемый ответ — `OK`. Этот эндпоинт не проверяет доступность баз и сервисов.
[Руководство по API](docs/api.md) содержит примеры запросов и сценарий проверки
остатка и повторного заказа. Полный HTTP-контракт: [OpenAPI](api/openapi.yaml).

## Наблюдаемость

Order предоставляет метрики на `http://localhost:9091/metrics`:
`orders_created_total`, `grpc_server_requests_total`, `grpc_server_duration_seconds`
и стандартные метрики Go/process. Счётчик заказов увеличивается после успешного
завершения создания платежа.

[Конфигурация Prometheus](monitoring/prometheus/prometheus.yml) опрашивает
`localhost:9091` каждые 15 секунд. При локальном запуске:

```bash
prometheus --config.file=monitoring/prometheus/prometheus.yml
```

Grafana может использовать Prometheus как источник данных. Запуск Grafana,
provisioning и дашборды в проект не включены.

## Проверки и тесты

```bash
go build ./...
go vet ./...
go test -count=1 ./...
```

Полный набор тестов требует доступа к Docker для PostgreSQL Testcontainers.
E2E включается отдельно и требует запущенных сервисов и тестовых баз.
[Руководство по тестированию](docs/testing.md) описывает запуск unit-тестов
без инфраструктуры и настройку E2E.

## Ограничения MVP

- Заказ содержит ровно одну позицию. Цена передаётся клиентом и не сверяется
  с Inventory; валюта проверяется на непустоту.
- Общей транзакции между сервисами нет. Ошибка после резервирования может
  оставить резерв, а ошибка платежа — сохранённый заказ без платежа.
  Автоматическая компенсация и восстановление не реализованы.
- Точный повтор заказа возвращает `409 Conflict`. Он не восстанавливает
  незавершённый платёж. Payment не сверяет сумму и валюту повторного запроса
  с уже сохранённой записью.
- Нет HTTP-аутентификации и TLS на Gateway; конфигурация рассчитана на локальную
  разработку. Gateway слушает все интерфейсы на порту 8080.
- Нет REST-чтения заказа, HTTP API Payment и операций пополнения товара.
  Учебный `WatchOrder` выдаёт демонстрационные статусы без чтения БД.
- В проекте есть Dockerfile для Order и Inventory и локальные kind-манифесты
  Inventory. Полный контейнерный запуск не подтверждён; Docker Compose отсутствует.

Подробности резервирования и идемпотентности: [архитектура](docs/architecture.md).
